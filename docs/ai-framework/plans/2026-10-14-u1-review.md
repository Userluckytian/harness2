## 审查面 1：悬挂收敛（store.ts）

### 1a) hungTimers 清理路径 —— **P1-2（已修）**

- **发现（P1）**：`removeSessionFromView`（`store.ts:407`，HEAD 版）不清 `hungTimers`——删除一个 running 会话后，≤30s 窗口内定时器仍会到点对已删流 `convergeHungTurn`（写合成终态 + 全局 `notify()` 空转）。按任务判据「泄漏=P1」定级。
- **修法**：`removeSessionFromView` 开头 clear+delete 该 id 定时器（`1492b99`）；用例 i 锁定（撤除后到点既不 notify 也不写 turnEnds）。
- **`disconnectWs` 路径**：核查 = 桌面**主进程** bridge 的 WS 关闭（`bridge.ts:399`），渲染端 store 无对应入口，不持有需清理的定时器；断流语义天然安全：帧停止 → 已挂定时器至多触发一次 converge（触发即从 Map 删除，`store.ts:305`），**无泄漏**。`applyReplay` 后定时器复用同表互斥（`armHungTurnWatch` 先 clear 后 set，一计时一会话）✓。
- 残留（P2-4）：`deleteSession` 不 `unsubscribe`、streams 缓存不清（既有软删设计，见 P2 清单）。

### 1b) `dropSyntheticEnd` 复活真终态？—— **OK**

`dropSyntheticEnd`（HEAD `store.ts:333-336`）仅当 `turnEnds[id]?.synthetic === true` 才删除——真 turn-end 帧写入的对象**恒无** `synthetic` 字段（`applyFrame` turn-end 分支整体赋值，字段来自 frame），绝不会被删。真帧→增量的正常覆盖链不受影响。用例 c′ 从反方向钉「合成被真帧整体覆盖」。✓

### 1c) 合成 `turnEndedAt` 与真帧写竞态 —— **OK**

JS 单线程，无真竞态；顺序语义逐条核过：

- 真帧先到（写 `turnEnds` + `turnEndedAt`，running=false）→ 定时器到点：`convergeHungTurn` 首行 `!running` return false，两表都不扰动（用例 c 钉「墙钟不许被扰动」）。
- 合成先到 → 真帧后到：`turnEnds` 整体替换（synthetic 消失）、`turnEndedAt` **改写为真帧到达时刻**——「已工作」时长口径从「悬挂 30s」切到真值，语义正确（真帧是权威）。
- 合成写入受 `turnEnds[turnId] === undefined` 守卫（`store.ts:321`），不覆盖已有真终态。

### 1d) 多会话并发互不干扰 —— **OK**

`hungTimers` 以 `stream.id` 为键（一计时一会话）；`convergeHungTurn` 只写传入 stream；`noteActivity` 只刷本流 `lastFrameAt`。跨会话唯一共享点 = 触发后的 `notify()`（全局快照语义，既有设计）。

### 1e) T4b 派生层防御 —— **OK**

`parseEventTs` 对 `undefined`/`''`/不可解析（`Number.isFinite`）三重防御；`workDurationMs` 仅在 `startedAt !== undefined && endedAt !== undefined` 才产；`turnEndedAt` 经 `work?.turnEndedAt?.[turnId]` 可选链（旧调用面不传 `work` 不炸，用例「不传 work 上下文」钉住）。

### 新发现 P1-1（本审查面最大缺口，已修）

**`running` 在帧内 `false→true` 翻转的两处漏挂表，悬挂永不收敛（痛点⑤原样复发）：**

1. `applyResumeSnapshot`（HEAD `store.ts:876`）：`stream.running = snap.activeAttempt !== undefined`。`applyFrame` 开头的 `noteActivity` 对表时 running 还是**旧值 false**（未挂表）；快照翻转 true 后**无任何补挂点**。这正是计划规格点名的「**重连后**无 turn-end 的 running 回合」正触发场景——断线重连补到在途 attempt、而 serve 静默死掉不再发帧 → 永不收敛、永久转圈。（对照：delta/text-delta/user-message 落盘/markSending 三处翻转都补挂了 `armHungTurnWatch`，唯独此处漏。）
2. `removeApproval`（HEAD `store.ts:960-968`）：审批等待期内定时器到点 → `convergeHungTurn` 因 `approvals.length > 0` 让路（**定时器已被消费、running 仍真、无重挂**）。审批被本地清除（用户点卡片）后，若无后续活帧（serve 恰死），永无收敛时机。

**修法**（`d12bddc`）：翻转/清审批处各补一次 `this.armHungTurnWatch(stream)`（该函数天然处理 running=false 撤表 / >阈值就地收敛）。用例 g（resume-snapshot 翻转→30s 收敛）、h（审批让路→removeApproval 重挂→30s 收敛）先红（h 修复前实测 FAIL）后绿。既有 e) 用例「审批移除后**下一活帧**起恢复」的补偿路径由此升级为「审批移除即刻重新对表」，语义严格增强，e 仍绿。
