> **元规范：** `docs/ai-framework/phased-plan-driven.md`

**Goal:** 让模型真正消费用户附件（图片/文本）并知道当前工作目录，同时保持「日志是唯一事实源、UI 零改动、core 只走批准的解冻窗口」。

**为什么现在做：** 真机测试中模型明确回复「没有收到图片附件」；日志证明 UI 上传成功、`adapter/user-attachments` 已记录 ref，但 `buildChatMessages` 只投 `user/message.text`。cwd 同理：`runTurn` 的 system 只含 memory/skills。两项都是用户直接可感知的缺口。

---

## 范围与非目标

**做：**

1. 图片附件 → provider 多模态 content parts（`image_url` / Anthropic image block），模型能描述图片。
2. 文本类附件（text/markdown）→ 读取内容内联进模型上下文（带字节上限与截断标记）。
3. 当前工作目录/工作区 → 注入 system prompt 的环境段。
4. 日志可重放：附件 ref 已落盘；图片/文本内容在请求组装时按 ref 读取，保证 Model-visible ⟺ logged。

**不做：**

- 不改 ZCode UI/协议；不新增 UI patch。
- 不做远端（SSH/WSL/Docker）附件、PDF 解析、音视频理解（PDF 可先如实占位/提示不支持）。
- 不做 provider 写路径、侧栏批量操作（ZS4）。
- 不把附件内容 base64 伪装成文本塞进 `user/message`（红线）。

## 架构

### 1. 附件内容组装（core 加性窗口 A）

- `ChatMessage.content` 从 `string` 扩展为 `string | ChatContentPart[]`：
  - `{ type: 'text', text }`
  - `{ type: 'image', mime, dataBase64 }`（provider 层再映射为 OpenAI `image_url` / Anthropic `source`）
- `buildChatMessages(session, options?)` 读取 `session.extensionEvents` 中已注册的 `adapter/user-attachments`，按 `turnId` 找到对应 user 消息，追加为 content parts。
- 内容解析经注入缝 `resolveAttachment?: (ref, mime) => Promise<ChatContentPart | null>`（由 adapter 提供），避免 core 直接做文件 IO/安全边界。
- 解析失败/超限/不支持类型 → 追加一条 `{type:'text', text:'[附件未加载: <fileName> (<reason>)]'}`，不伪造内容。

### 2. 环境上下文（core 加性窗口 B）

- `RunTurnOptions.environment?: { cwd: string; workspacePath?: string; platform?: string }`
- loop 在 system 文本前追加固定短段：
  `[环境] 当前工作目录: <cwd>；工作区: <workspacePath>；平台: <platform>。`
- 与 memory/skills 同属稳定前缀；无 environment = 旧行为不变。

### 3. adapter 解析器

- 读取 ref：优先 `~/.harness2/zs/attachments` 下的已提交文件；本地零拷贝路径在发送时复制进该目录，保证会话可重放。
- 图片：MIME 白名单（png/jpeg/webp/gif），单图 ≤ 5 MiB，超限/未知 → 占位。
- 文本：`text/plain`、`text/markdown`，≤ 256 KiB，超出截断并标注。
- 密钥/敏感数据：只读附件路径，错误经 `redactSecrets`。
