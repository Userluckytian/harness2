# 协作与分工模式（对全部后续阶段生效）

> 制定：2026-09-06 · 由项目负责人确认 · 交接必读
> 目的：明确"谁做什么"，保证任何接手者（人或 AI 会话）都能按同一模式继续。

## 角色分工（硬规则）

| 角色                   | 由谁承担                      | 职责                                                                                                                  | 明确不做                               |
| ---------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| **编排者**（主会话）   | 主对话 AI                     | 阶段计划起草与更新、任务分发与全局把控、**验收**（对照计划重跑证据命令）、文档与进度更新（每日日志/ROADMAP/交接文档） | **不直接写功能代码、不跑测试驱动开发** |
| **实现代理**（子代理） | general-purpose agent         | 按阶段计划（交接提示词）独立实现代码与测试，每 Task 验证后按规范 commit                                               | 不改计划、不扩大范围、不 push          |
| **测试代理**（子代理） | general-purpose agent         | 补测试、跑全量验证、报告实际输出                                                                                      | 不虚构结果                             |
| **审查代理**（子代理） | general-purpose agent（只读） | 按 CODE_REVIEW.md 独立审查 diff，按 P0/P1/P2 输出发现与 verdict                                                       | 不修改文件                             |
| **人类**               | 项目负责人                    | 方向决策、技术栈与范围确认、`git push` 授权、跨阶段优先级调整                                                         | —                                      |

## 每阶段标准流程

```
1. 编排者起草阶段计划（含零上下文交接提示词）→ docs/ai-framework/plans/YYYY-MM-DD-phase-<slug>.md
2. 编排者派【实现代理】执行计划全文（提示词即计划文末的「给接手 AI 的完整提示词」）
3. 编排者派【审查代理】审查分支 diff（对照计划 + CODE_REVIEW.md）
4. 有 P0/P1 → 回到步骤 2 派修复任务（只修发现项）；P2 → 记入残留风险
5. 编排者验收：亲自重跑验收表全部证据命令 → 通过则计划状态改「已完成」
6. 编排者更新文档：阶段计划状态、ROADMAP 功能状态列、每日日志、HANDOFF.md 快照
```

## 验收规则（编排者不可委托、不可省略）

1. 验收表每一条都必须由编排者**在本机重跑**对应命令，以实际 exit code/输出为准；禁止采信「应该能过」。
2. 红线检查（密钥不入库、append-only 等架构不变量）纳入每次验收。
3. 验收结论与证据写入每日日志；缺陷显式带入下阶段，不许口头略过。

## 子代理调度纪律（2026-09-06 补充，故障复盘结论）

1. **同一时刻至多 1 个子代理**（用户确认）：流水线各环节串行派发；例外仅限"两个互不写文件的只读审查"，且派发前需确认无长任务在跑。
2. **失败重试阶梯**：子代理故障（并发限制/网络）→ 等 20s 重试一次 → 仍失败则**派微型探针**（一条命令的 Explore 代理）测健康 → 探针通则重派原任务，探针也挂则降级为编排者代做并全程留档。
3. **中断接手**：长任务被中断后先查 `git status/log`——已完成提交的部分不重做，未提交改动交新代理"核对-补全-修红-验证-提交"（两轮实操已验证此流程）。
4. **降级留档三件套**：代做事项写入 issue-log（含"待补独立审查"）、diary 记录经过、OPEN.md 登记补审待办——基础设施恢复后优先补审。

## 交接要求（文档自包含）

1. **入口唯一**：新维护者/AI 从 `docs/HANDOFF.md` 进入 → `AGENTS.md` → 当前阶段计划。
2. 所有计划文档必须含「零上下文交接提示词」，使实现代理不需要任何会话记忆即可开工。
3. 关键决策记录在 `docs/ROADMAP.md`（D1-D6）与 `architecture.md`，禁止只存在于对话中。
4. 每日日志（`docs/diary/`）是发版 release note 的素材源，必须可独立读懂。
5. 子代理是临时会话：**任何只在子代理上下文里的信息都视为已丢失**，重要结论必须回写到文档。
