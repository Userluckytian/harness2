### 1.3 根因（已在 Linux 上确定性证明）

`packages/gateway/src/serve-client.ts`：

```ts
126:        socket.on('open', () => {
127:          this.ws = socket;          // ← 只有 'open' 之后才记录套接字
...
205:  close(): void {
206:    this.closed = true;
...
211:    if (this.ws !== null) {          // ← 若 'open' 尚未触发，this.ws === null
212:      try { this.ws.close(); } catch {}
213:      this.ws = null;
214:    }
215:  }
```

竞态窗口：测试在**服务端**观察到连接（`connected >= 1`）后立刻 `handle.stop()`。若此刻**客户端 socket 的 `'open'` 回调尚未执行**，`this.ws` 仍为 `null` → `close()` **什么都不关**；而 `'open'` 回调也**不检查 `this.closed`** → 套接字被**孤儿化**：服务端永远收不到 `close`（正是日志里的 3s 超时）。这在生产上等于「网关 stop 后仍有一条 WS 活着、`onFrame` 继续回调」。

**附加面**：该孤儿 socket 后续若触发 `'error'`，`socket.on('error')` 中 `this.ws !== socket` 成立 → `reject(e)` 一个**无人 await** 的 `readyPromise` → unhandled rejection（本次第一版复现脚本在清理阶段正是被这条判红）。

**确定性复现（仅 WSL 临时副本，未入仓）：**

```
[PROOF-A] close() immediately after connect(): connected=1 closed=0   ← 泄漏复现
[PROOF-B] close() after waitReady():          connected=1 closed=1   ← 正常路径
```

### 1.4 修法建议（**由 gateway owner / 解冻后执行**，T 轨不得改）

1. **主修**：让 `close()` 能取消「在途连接」。最小改动：在 `connect()` 内保存 `this.pending = socket`，`close()` 中 `this.pending?.terminate()`；或（更稳）在 `'open'` 回调首行加 `if (this.closed) { socket.close(); return; }`。
2. **防 unhandled rejection**：`'error'` 分支不要 reject 一个无人消费的 promise（`close()` 时把该 promise 标记为已处理，或在 `readyPromise` 上挂 `catch` 兜底）。
3. **测试侧稳健化（次要，不建议单独用）**：`gateway-lifecycle.test.ts` 在 `stop()` 前改为「等服务端连接**且客户端已 open**」再停；并保留 3s 预算。根因在实现，只改测试会留生产缺陷。
4. **门禁**：把 B1 登记为 gateway 的解冻修补项（P1），并在修补前用「重跑」通过 CI 门槛——该缺陷是竞态，重跑有较大概率转绿。

### P2-3 无 `SIGTERM` / `SIGHUP` 的终端恢复路径

- **文件：** `packages/cli/src/tui/runInkChat.tsx:145-167`（`createShutdown` + `render(..., { exitOnCtrlC: false, alternateScreen })`）
- **问题：** in-app 退出（`/exit`、Ctrl+C 确认、EOF）路径是**正确的**：`finish()` 先 `app.unmount()`（ink 拆 alt screen / 复原 raw）再 `runtime.finish()`，且 `exit()` 只写 `process.exitCode` 不 abrupt exit。但**没有** `process.on('SIGTERM'|'SIGHUP')` 处理：Node 对信号的默认动作**不会**触发 `process.on('exit')`，故 `kill <pid>` / 终端被强关时可能把终端留在 raw + alt screen 态（需 `reset` 才能恢复）。
- **修法：** 注册 `process.once('SIGTERM'|'SIGHUP', () => shutdown.request('error'))`（或 `sigint`），复用同一幂等闸。
- **严重度：** P2（真机才可判定；计划已把 raw mode 进出列为手工验收项）。

## 7. 遗留风险

1. **B1（最高）**：`ServeClient.close()` 在途连接竞态是**生产缺陷**（stop 后套接字孤儿化 + 可能 unhandled rejection），目前仅以「偶发 CI 红」暴露。在冻结区内，本轨不能修；建议编排者优先「重跑 CI」清门禁，并把该项作为 gateway 解冻后的必修项。
2. **CI 稳定性**：`packages/gateway` 无 `vitest.config`（默认 5s 超时）、`packages/desktop` 未设 `testTimeout`（core/cli 均为 30s，且 core 配置注释误称 desktop 也是 30s）。`pnpm -r test` 下四包**并发**跑（已实测日志交错），4 vCPU runner 上 5s 默认超时的套件是下一类脆弱点——建议编排者统一超时口径（属根级/他包，超出本轨边界，仅登记）。
3. **真机未验**：raw mode 进出、中文宽度、Ctrl+C 恢复、IME、Shift+Enter 四环境手感仍无录屏/截图证据（计划内手工项）。
4. **steer 重复实现**：语义已逐条等价（§3.1），但重复代码会随 core 演进漂移；建议按实现者 §7-1 的建议在解冻窗口导出 `SessionSteerSink` 后改为导入。
5. **cell 级残留**：`useTurnStream` 50ms flush timer 无 unmount 清理（P2-1）。
