### 4.1 失败明细（3 项，全部 `test/fork.test.ts` hub/HTTP/WS 分叉入口）

三条用例均抛 `ServeLockError`：

```
ServeLockError: serve 端口锁被占用（pid 39984, port 61753）；如需接管请先停止既有 harness2 serve
    acquireServeLock src/server/http.ts:104:11  ← isPidAlive(39984)=true
```

### 4.2 根因（环境遗留，非本 Task/S0 引入；本 Task 不碰 server/*）

- 机器 `%USERPROFILE%\.harness2\serve.lock` 内容：`{"pid":39984,"port":61753,"ts":"2026-09-07T16:25:54.118Z"}`。
- 调查：`Get-Process -Id 39984` → **进程不存在**（"找不到进程标识为 39984 的进程"）；`tasklist /FI "PID eq 39984"` 同样无匹配。
- 即：该锁是**陈旧锁**（2026-09-07 遗留），PID 39984 已被系统回收，运行时被 `isPidAlive` 误判为存活（探活语义为 `process.kill(pid,0)`，属已知 Windows 陈旧锁误判窗口），启动测试 server 抛 `ServeLockError`。
- 其余全部 `startServe` 测试（assembly/cron/server/trust/ws）都传了 `home` 参数隔离锁目录，只有 `fork.test.ts` 三处 `startServe` 未传 `home`（用真实 `~/.harness2` 锁），故仅这三个用例受波及。

### 4.3 处置（显式列旧失败，不归咎环境后跳过）

- **不在 S0 静默跳过**：本文件如实记录失败与根因；`fork.test` 锁隔离缺口应归共享后续 Task 或终端轨修复（建议：`startServe` 三处补 `home` 临时目录，与其它测试一致）。
- 本 Task（S0）文件范围不含 `server/*` 与 `test/fork.test.ts`，不擅改。
- 该陈旧锁 + PID 回收属**瞬时窗口**：改动后全量复核时同一批 `fork.test` 三用例已随 PID 39984 真死而转绿（见 §5 末行），旧失败与实现无关，但仍在此显式留档（不「归咎环境后跳过不做记录」）。
