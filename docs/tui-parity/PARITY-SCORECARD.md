## 评分口径（V0 估值是怎么来的——照此可复算）

1. 逐场景打开 `out/<场景>/{ours,grok}/*.txt` 双侧网格，以 `docs/tui-parity/matrix.md` 该场景的「维度表」为差异清单。
2. **每个仍然不同的维度 −8%**；`matrix.md` 改进清单里标 `✅ 已修`（P11 完成并附前后抓屏）的项不再计入；`⬜ 待排期`/`📌 已登记` 计为仍然不同。
3. **内容差异不扣分**（模型不同、回复文本不同），一律进「豁免格清单」。
4. **我方优势项不扣分**（`[end_turn · steps · toolCalls]` 汇总行、子任务卡片信息量、失败态独立结果行），同样进豁免格。
5. 双侧或单侧**全空的帧**额外 −8%，并在「状态」列标出，等 V1-A 修等待窗口后重抓。
6. 结果写成 `~NN%` 形式 —— 它是**估值**，不是实测。V1-A 的 `diff.py` 出来后，本列须被逐格实测值整体替换。

## 结构指纹基线（2026-09-17 实测，非估值）

上表的估值太粗，所以同时留一组**可复算的客观数字**。V1-A 的 `diff.py` 出来后，这些数字应当能被独立复现，作为对 `diff.py` 的交叉校验。统计法：逐帧读 `.txt`，`非空行` = 去掉全空白行后的行数，`宽` = 最长行字符数，`框线` = 框线/制表类字符总数，`实字` = 去掉所有空白后的**字符**数（中文按 1 计，不是字节数）。数据由 V0 于 2026-09-17 用一次性脚本实测（脚本只读，不改仓库产物）。

| 场景                | 帧                    | 我方非空行/宽/框线/实字 | grok 非空行/宽/框线/实字 | 读法                                                            |
| ------------------- | --------------------- | ----------------------- | ------------------------ | --------------------------------------------------------------- |
| A1-cold-start       | `01-cold-start`       | 29 / 110 / 135 / 374    | 16 / 110 / 407 / 683     | grok 用框线搭出输入框与引导卡，我方框线只有其 1/3，实字也少一半 |
| B1-stream-midshot   | `02-reply-done`       | 29 / 110 / 28 / 384     | 8 / 109 / 178 / 394      | 实字量接近，但我方把 30 行画满、grok 回合结束后只留 8 行        |
| C1-slash-candidates | `01-slash-candidates` | 29 / 110 / 20 / 360     | 15 / 109 / 394 / 860     | grok 候选区带分隔线与说明列：框线密度约为我方 20 倍             |
| C2-help-and-unknown | `01-help`             | 29 / 110 / 11 / 1049    | 10 / 109 / 395 / 751     | 我方 help 是纯文本（实字反而更多），grok 是分组带框             |
| D1-tool-cards       | `01-tool-cards`       | 29 / 110 / 28 / 380     | 9 / 109 / 179 / 469      | grok 侧另有 `00-welcome`（21 / 110 / 417）无我方对照帧          |
| G1-status-line      | `01-idle-status`      | 29 / 110 / 135 / 375    | 21 / 110 / 417 / 867     | 状态行字段顺序与位置差异见 `matrix.md` §G                       |
| K2-canvas-160x40    | `01-idle`             | 39 / 160 / 195 / 437    | 21 / 160 / 561 / 1020    | 160 宽下我方画满 39 行，grok 21 行                              |

> **两条从这张表里才能看见、`matrix.md` 没写的结论**（V0 新发现，已进 OPEN.md 第一节）：
> ① **屏幕填充度差异**：我方几乎每帧都画满整个画布（29/39 行非空，主要因为最右列常驻竖线逐行占位），grok 空闲帧只有 5~~21 行。
> ② **框线用量差一个数量级**：grok 每帧 178~~561 个框线字符，我方 11~195 个。P11 修的是 `❯` 锚点 + 空态占位，**并没有真的加边框**——这与 `matrix.md` A 段「grok 是完整输入框」仍然对不上，是 V2 的活。

## 配色为何未测

- 计划的 Task 5 让「打开每个场景两侧的 `.txt` 肉眼过一遍」估两个分——但 **`.txt` 是纯字符网格，不含任何颜色信息**，配色估值无法从权威数据源得出，故本列 V0 一律留空并写明原因（诚实红线第 3 条）。
- 已知的唯一硬结论来自 `docs/ai-framework/plans/2026-09-15-p12-backlog.md` 的 C6（提交 `aecd176`）：**全链路 fg-only**——`CellBuffer` 只有 `chars/widths/fg/linkIds`（无 bg 属性位）、`DiffPresenter` 只发射前景 SGR、全仓无 `48;2` 背景序列；且 **grok 同样无背景色**。所以「背景色」不是复刻缺口，是超出参考实现的自选增强。
- 要给这一列填数，V1-A 需二选一：① `diff.py` 加**逐格 fg 比对**（从抓屏台多导一份颜色层）；② 人眼读 PNG 对（PNG 含颜色，但按 README 口径只能作辅助，不得单独作结论）。
