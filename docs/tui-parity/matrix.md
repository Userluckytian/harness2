# 逐场景差异对照表（next 壳 vs grok 1.0.13）

> 证据口径：`.txt` 屏幕网格为权威（逐格保真），PNG 见 [`images/`](images/)。
> 严重度：**P0** 明显不可用/功能性误导 · **P1** 体验显著落后参考实现 · **P2** 细节差异 · **优势** 我方更好。
> 方法与边界见 [`README.md`](README.md)。

## 0. 抓屏可信度验证（为什么可以据此下结论）

我方 `/help` 首屏出现文字重叠。为区分"真实渲染缺陷"与"抓屏器保真度不足"，做了一次**宽度表交叉验证**：

1. 取 `/help` 屏幕网格里出现的全部 **302 个字符**；
2. 用我方渲染器的 `charWidth()`（`packages/cli/dist/tui/renderer/cell-buffer.js`）求显示宽度；
3. 用终端仿真器 pyte 实际使用的 `wcwidth` 求显示宽度；
4. 逐字符比对：**不一致仅 1 个 —— `\r`（我方 1 / wcwidth -1，控制字符，不参与绘制）**。

宽度表一致 ⇒ 仿真器对我方输出序列的解释与真实终端一致 ⇒ **网格里的重叠就是真实终端会呈现的画面**。
另用「空白屏第一次 `/help`」实验排除了"未擦除上一帧"的解释（首次渲染即错位）。

> ️ **版面变更事实**：P10 之前 TTY 默认进的是**旧壳**（顶部状态条 + 带边框输入框 + 框内 `Enter 发送 · Shift+Enter 换行` 提示），
> `next` 需 `HARNESS2_RENDERER=next` 才启用。删掉旧壳后**默认 UI 变成了 next**——上表就是用户现在实际看到的版面，
> 其中「输入区空态不可见」是相对旧壳的明显退步。

- **P1 输入区无任何视觉提示（首用可见性）**：空态下无边框、无 `>` 提示符、无占位符、光标不可见——
  新用户打开后不知道在哪里打字（grok 的输入框带边框 + `>` + 模型名）。
  证据：`images/p11/evidence/ours-idle-empty.png` vs `ours-draft.png`（空态 vs 有草稿，含同名 `.txt` 网格）。建议草稿行加 `❯`/`>` 前缀或细边框，空态给占位提示。
- **P1 冷启动无引导**：新用户看不到任何"能按什么、能去哪"。
  建议：首屏加一次性引导卡（可 `[ui] show_welcome=false` 关闭），列 4~6 个最常用键与命令。
- **P2 缺仓库/分支与 token 预算**：我们有 cwd 与 ctx%，缺 branch 与 token 上限。
- **P2 会话 id 常显**：对用户无意义（grok 用标题），建议降级到底部状态行或 `/status`。

- 说明：B1 流式中间帧我方为打字机增量 + 光标；grok 在 +5s 时尚未出现任何占位（时序受限，**不定论**）。

## I 撤销 / J 队列 / L 失败（grok 侧已用 big-pickle 补抓）

> 补抓背景：grok 侧原来的模型较慢、按 mock 调的等待窗口常抓到空帧；换成本地 40080 端点的 `big-pickle`
> 后单轮约 3~4 秒（实测 `grok -p` 3.7s），四组场景均已拿到帧。

| 组                   | 我方                                                                                            | grok                                                                                                                                                             | 结论                                                                                                                                                                             |
| -------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **I 撤销**           | `/undo`（投影截断 + 文件快照回滚，带 `--dry-run`）与 `/redo`                                    | **没有 `/undo` `/redo`**；命令面是 **`/rewind <prompt>`**（官方文档：“Rewind to a previous prompt (restores files)”，会话目录同样落 `rewind_points.jsonl` 快照） | **P2 交互模型差异**：grok 以“指定历史 prompt”为锚点回退；我们以“撤销最近 N 轮”为锚点且支持 redo。两者都落快照，语义方向一致。建议：保留我们的语义，补一个 `/rewind <序号         | prompt>` 别名（降低从 grok 迁移的肌肉记忆成本） |
| **J 队列**           | 忙碌时回车排队 → 排空后按序执行（2 帧）                                                         | 忙碌态**提示行把自己改写了**：`Enter:queue │ Alt+Enter:newline │ Shift+Tab:mode │ Esc:cancel │ Ctrl+Enter:send now │ Ctrl+x:`；空闲态则是 `Enter:send │ …`       | **差距在信息密度**：两边都随状态改写提示行（我方 busy 分支为 `Ctrl+C 取消` / `Ctrl+; 队列(N)`），但 grok 连“Enter 是发送还是排队”、插队立即发（`Ctrl+Enter:send now`）都写进去了 |
| **L 失败**           | 工具失败：`└ ✗ read failed: ENOENT: no such file or directory, open '…no-such-file-parity.txt'` | 未复现（脚本的 `hi` 未提交：帧内 grok 仍在工作，且把斜杠输入交给了技能/命令路由，如 `/subagent-driven-development`、`Writing command…`、`Preparing read_file…`） | 待定性：grok 的失败态需要更贴合的剧本（直接让它读一个不存在的文件）。**已登记待补**                                                                                              |
| E 审批 / L2 模型报错 | —                                                                                               | —                                                                                                                                                                | ⬜ `defined_only`（mock 自动放行/不报错），待真机或真实 key                                                                                                                      |

> 补抓时另一个观察（已归入 P2）：grok 的斜杠输入带**技能/命令路由**——未识别的 `/xxx` 会被当命令/技能尝试执行
> （帧内出现 `Writing command… 1.3s`、`Preparing read_file… 0.2s`、`Waiting for response…`），而我们是直接报“未知命令”。
