# 逐场景差异对照表（next 壳 vs grok 1.0.13）

> 证据口径：`.txt` 屏幕网格为权威（逐格保真），PNG 见 [`images/`](images/)。
> 严重度：**P0** 明显不可用/功能性误导 · **P1** 体验显著落后参考实现 · **P2** 细节差异 · **优势** 我方更好。
> 方法与边界见 [`README.md`](README.md)。

## 0. 抓屏可信度验证（为什么可以据此下结论）

我方 `/help` 首屏出现文字重叠。为区分"真实渲染缺陷"与"抓屏器保真度不足"，做了一次**宽度表交叉验证**：

1. 取 `/help` 屏幕网格里出现的全部 **302 个字符**；
2. 用我方渲染器的 `charWidth()`（`packages/cli/dist/tui/renderer/cell-buffer.js`）求显示宽度；
3. 用终端仿真器 pyte 实际使用的 `wcwidth` 求显示宽度；
4. 逐字符比对：**不一致仅 1 个 —— `\r`（我方 1 / wcwidth -1，控制字符，不参与绘制）**。

宽度表一致 ⇒ 仿真器对我方输出序列的解释与真实终端一致 ⇒ **网格里的重叠就是真实终端会呈现的画面**。
另用「空白屏第一次 `/help`」实验排除了"未擦除上一帧"的解释（首次渲染即错位）。

## A 启动首屏

| 维度     | 我方 next 壳                                      | grok 1.0.13                                                                                      |
| -------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 顶部     | `[normal] \| <cwd> … ctx 0%`（常驻状态行）        | `≡ <branch> <cwd…>` + 右对齐 `1.5K / 1.0M`（token 预算）                                         |
| 会话信息 | `会话: 20260915-154537-635791（新建）` 常显       | 不显会话 id（标题/分支代替）                                                                     |
| 欢迎引导 | **无**                                            | 欢迎卡：版本号、Changelog、`New worktree ctrl+w` / `Resume session f3` / `Quit ctrl+q`           |
| 输入区   | 独立框 + 固定提示 `Enter 发送 · Shift+Enter 换行` | 框内右嵌 `Muse Spark 1.3 (40080) · always-approve`，框下提示 `Shift+Tab:mode │ Ctrl+x:shortcuts` |

- **P1 冷启动无引导**：新用户看不到任何"能按什么、能去哪"。
  建议：首屏加一次性引导卡（可 `[ui] show_welcome=false` 关闭），列 4~6 个最常用键与命令。
- **P2 缺仓库/分支与 token 预算**：我们有 cwd 与 ctx%，缺 branch 与 token 上限。
- **P2 会话 id 常显**：对用户无意义（grok 用标题），建议降级到底部状态行或 `/status`。

## B 对话

| 维度     | 我方                                                         | grok                                 |
| -------- | ------------------------------------------------------------ | ------------------------------------ |
| 用户消息 | `❯ hi`                                                       | `  hi` + **右对齐时间戳** `11:48 PM` |
| 助手消息 | 正文                                                         | 正文 + **右对齐时间戳**              |
| 本轮耗时 | **无**                                                       | `Worked for 9.9s`                    |
| 用量     | **无**（仅 `ctx 0%`）                                        | 头部 `15K / 1.0M`，忙碌时 `↓15.6k`   |
| 回合汇总 | `[end_turn · steps 3 · toolCalls 2]`（**我方优势**：结构化） | 无对应行                             |

- **P1 缺时间戳/耗时/用量**：这是 grok 体验的核心三件套，尤其"这轮花了多久、烧了多少"。
  建议：消息行尾加相对时间（或开关）；每轮结束加 `Worked for Xs`；头部或状态行加 `used / total`。
- **优势**：`[end_turn · steps · toolCalls]` 保留（grok 无），可放在与耗时同一行。
- 说明：B1 流式中间帧我方为打字机增量 + 光标；grok 在 +5s 时尚未出现任何占位（时序受限，**不定论**）。

| 列表位置     | 提示行上方                                                   | 输入框上方，带分隔线                                                               |
| 列表下方提示 | `/ 命令 · Tab 焦点 · Ctrl+C 退出`                            | `Enter:send │ Alt+Enter:newline │ Shift+Tab:mode │ Ctrl+x:shortcuts`               |

| 未知命令     | `未知命令 /no-such-command（/help 查看命令列表）`            | 未报错，转而让模型处理（帧内显示 `Writing command… 1.3s`、`Esc:cancel`、`[stop]`） |

- **P0 `/help` 渲染错位** —— 见 `images/C2-help-ours-BUG.png`（首屏第一次渲染即错位，非残留；宽度表已验证一致）。
  影响：最核心的自助入口不可读。
  建议：作为修复阶段的第一优先项；修复后在 `packages/cli/test/tui/next/` 增加**布局断言**
  （如"渲染帧任意两行不得出现同一文本片段的交叉"或对 help 面板做逐格快照），防止回归。
- **P1 候选列表缺说明**：grok 右列说明对上手帮助极大。建议两列 + 灰色说明；宽度不足时退化为单列。
- **P2 未知命令语义差异**：需先确认 grok 的确切行为（疑为交给模型/技能匹配）再决定是否对齐；
  我方当前"明确报错"对新手更安全，建议**保留但补充近似建议**（`/no-such-command` → 最接近的 `/xxx`？）。

## D 工具调用

| 维度     | 我方                                               | grok                                      |
| -------- | -------------------------------------------------- | ----------------------------------------- |
| 形态     | 两行树形：`⏺ write(harness2-demo.txt)` + `  └ ✓`   | 单行：`♦ Listed 1 dir` / `♦ Read 1 skill` |
| 信息     | **工具名 + JSON 参数**（`write({"file_path":…})`） | 人类动词短语 + 数量 + 名词                |
| 结果     | 独立结果行（`└ ✓` / `└ ✗ …`）                      | 合并进同一行（失败态未取到）              |
| 明细展开 | `Tab` 切焦点 + `Shift+E` 展开（已实测）            | 未取到展开态                              |

- **P1 工具行可读性**：面向用户应给"做了什么"，不应暴露 `{"file_path": ...}`。
  建议：主行给动词短语（"写入 harness2-demo.txt"），参数与 JSON 移入展开态。
- **优势**：我方"卡片 + 结果行"在失败时更清楚（`└ ✗ read failed: ENOENT: … no-such-file-parity.txt`）。
  建议保留结构，只改主行文案。
